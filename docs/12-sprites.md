# 12. 캐릭터 스프라이트 — 도트 명세

> Piskel에서 도트 단위로 설계하고 확정한 데이터. 아래 매트릭스는 **그대로 코드로 옮길 수 있다.**
> 뷰어: [`sprites.html`](sprites.html) · 규격: 32×32, 논리 해상도 480×270 기준

---

## 12.1 규격

| 항목 | 값 |
|---|---|
| 캔버스 | 32 × 32 px |
| 캐릭터 점유 | 가로 16 px (어깨 최대), 세로 27 px (y4~y30) |
| 비율 | 머리 8 : 몸통 11 : 다리 8 |
| 발끝 | y30 — 이 줄이 지면에 닿는다 |
| 기준선 | 세로 중심 x15/x16 |

### 도트 원칙

32px에서 지킨 규칙. 어기면 실루엣이 무너진다.

1. **아웃라인은 실루엣 바깥에만.** 팔과 몸통 경계는 아웃라인이 아니라 그림자색(`4`)으로 나눈다. 3px 팔에 양쪽 아웃라인을 넣으면 팔이 검은 막대가 된다.
2. **그림자색은 아웃라인과 명도가 붙지 않게.** `4`(#5F6E85)는 아웃라인(#0B0710)과 충분히 떨어져 있다.
3. **뼈는 빈 공간으로 그린다.** 백골의 갈비는 선과 투명이 번갈아야 뼈로 읽힌다. 채우면 흰 덩어리가 된다.
4. **어깨는 역삼각형 곡선.** 폭이 행마다 변해야 한다(8→12→16→14). 같은 폭을 반복하면 냉장고가 된다.

## 12.6 측면 뷰 — 실제 플레이 스프라이트

> **정면 뷰(12.3~12.5)는 타이틀·메뉴·결과 화면용이다.**
> 측면 스크롤 게임의 플레이 스프라이트는 처음부터 측면으로 설계해야 한다.
> 정면 뷰로 걷기를 만들면 다리가 좌우로 교차해버린다 — 실제로 한 번 겪고 다시 그렸다.

### 파츠 9개

프레임마다 도트를 새로 찍지 않는다. 파츠를 오프셋만 바꿔 조립한다.
동작을 늘려도 작업량이 거의 늘지 않는 것이 이 방식의 핵심이다.

```ts
export const PARTS = {
  PLUME:  ['....78','..7888','.78880','788...'],
  HEAD:   ['...000000...','..01222220..','.0122222220.','012222BBB220',
           '012222222220','.01222222220','..012222220.','...004400...'],
  TORSO:  ['.01222210.','0122222210','0122222210','0122222210','0123333210',
           '0123333210','0122222210','0122222210','.01222210.','0123333210'],
  ARM_F:  ['4220','4220','4220','4220','4110','.00.'],
  ARM_B:  ['0344','0344','0344','0344','0114','.00.'],
  LEG_F:  ['4220','4220','4220','4330','4330','4330','4330'],
  LEG_B:  ['0344','0344','0344','0334','0334','0334','0334'],
  BOOT_F: ['42220','42220'],
  BOOT_B: ['03444','03444'],
}
```

| 파츠 | 기준 위치 | 크기 | 가동 축 |
|---|---|---|---|
| `PLUME` | (4, 2) | 6×4 | 몸통 따라 상하 |
| `HEAD` | (9, 4) | 12×8 | 몸통 따라 상하 |
| `TORSO` | (10, 12) | 10×10 | 상하 (바운스·웅크리기) |
| `ARM_F` | (17, 15) | 4×6 | 좌우 + 상하 (공격의 주역) |
| `ARM_B` | (8, 15) | 4×6 | 좌우 (걷기 반대 위상) |
| `LEG_F` | (15, 22) | 4×7 | 좌우 (보폭) |
| `LEG_B` | (10, 22) | 4×7 | 좌우 (반대 보폭) |
| `BOOT_F` | (15, 29) | 5×2 | 앞다리 따라감 |
| `BOOT_B` | (9, 29) | 5×2 | 뒷다리 따라감 |

**뒷팔·뒷다리는 어두운 색(`3`,`4`)으로 그린다.** 측면 픽셀아트에서 앞뒤를 구분하는 표준 기법이며,
이것 없이는 걷기에서 두 다리가 한 덩어리로 보인다.

### 조립 순서

뒤에서 앞으로. 순서가 바뀌면 앞팔이 몸통에 가려진다.

```
ARM_B → LEG_B → BOOT_B → PLUME → TORSO → HEAD → LEG_F → BOOT_F → ARM_F
```

### 포즈 생성

```ts
type Pose = {
  dy?: number                    // 전신 상하
  lean?: number                  // 상체(투구·몸통·머리)만 좌우 — 젖힘
  af?: number; afy?: number      // 앞팔 좌우 · 상하
  ab?: number; aby?: number      // 뒷팔 좌우 · 상하
  lf?: number; lfy?: number      // 앞다리 좌우 · 상하
  lb?: number; lby?: number      // 뒷다리 좌우 · 상하
  legY?: number                  // 두 다리 공통 상하 (웅크리기·착지)
}

export function pose(o: Pose = {}): string[] {
  const { dy = 0, lean = 0, lf = 0, lb = 0, af = 0, ab = 0,
          afy = 0, aby = 0, lfy = 0, lby = 0, legY = 0 } = o
  const g = blank()
  stamp(g, PARTS.ARM_B,  8 + ab,   15 + dy + aby)
  stamp(g, PARTS.LEG_B,  10 + lb,  22 + dy + legY + lby)
  stamp(g, PARTS.BOOT_B, 9 + lb,   29 + dy + legY + lby)
  stamp(g, PARTS.PLUME,  4 + lean, 2 + dy)
  stamp(g, PARTS.TORSO,  10 + lean, 12 + dy)
  stamp(g, PARTS.HEAD,   9 + lean,  4 + dy)
  stamp(g, PARTS.LEG_F,  15 + lf,  22 + dy + legY + lfy)
  stamp(g, PARTS.BOOT_F, 15 + lf,  29 + dy + legY + lfy)
  stamp(g, PARTS.ARM_F,  17 + af,  15 + dy + afy)
  return g.map(r => r.join(''))
}
```

### 오프셋 유효 범위 — 넘기면 파츠가 떨어진다

같은 실패를 세 번 했다. 그림의 날개, 캐른의 팔, 착지 클립의 뒷팔이 전부
**파츠가 몸통과 겹치지 않아 따로 떠 보이는** 문제였다. 원인이 매번 같으니 수치로 못박는다.

몸통은 `x10~19`, `y12~21` 을 차지한다. 팔·다리는 이 범위와 **최소 1px 겹쳐야** 붙어 보인다.

| 축 | 안전 범위 | 한계 | 넘으면 |
|---|---|---|---|
| `af` 앞팔 좌우 | −4 ~ +2 | +2 | 어깨가 몸통 오른쪽 밖으로 나가 분리 |
| `ab` 뒷팔 좌우 | **−1** ~ +3 | −1 | −2 부터 뒷팔이 몸통 왼쪽에 뜬다 |
| `afy` `aby` 팔 상하 | −6 ~ +3 | −6 | 더 올리면 어깨가 몸통 위로 빠진다 |
| `lf` `lb` 다리 좌우 | −2 ~ +2 | ±2 | 걷기 보폭의 한계이기도 하다 |
| `lfy` `lby` 다리 상하 | −3 ~ +1 | +1 | 양수면 골반에 틈이 벌어진다 |
| `lean` 상체 좌우 | −3 ~ +3 | ±3 | 상체가 골반에서 떨어진다 |

> **`ab` 의 하한이 −1 인 것이 함정이다.** 앞팔은 −4 까지 가는데 뒷팔은 −1 이 한계다.
> 뒷팔 기준 위치가 `x8` 이라 몸통 왼쪽 끝(`x10`)과 3px 밖에 안 겹치기 때문이다.

이동·점프 입력이 전부 받아들여진다. 착지 경직은 "재시작 마찰 제거"와 정면으로 부딪힌다.

### 무기 7종 — 던지기 액션

무기는 **던지기 클립에서만** 화면에 나타난다. 원작처럼 평소에는 들고 있지 않다.

```ts
export const WEAPONS = {
  lance:  ['.........1','0222222211'],
  dagger: ['......1','0222211'],
  axe:    ['.111.','11311','.020.','..0..','..0..'],
  cross:  ['..1..','..1..','11111','..1..','..1..'],
  torch:  ['.77.','7887','.88.','.03.','.03.'],
  discus: ['.111.','12221','12021','12221','.111.'],
  hammer: ['.222.','23332','.030.','..3..','..3..'],
}
```

던지기 4프레임에서 무기가 손을 떠나 화면 밖으로 나간다. `wpn`은 무기 스프라이트의 좌상단 좌표다.

| 프레임 | 팔 | 무기 위치 | 의미 |
|---|---|---|---|
| 1 | `af:-2, afy:1` | `[12, 19]` | 준비 — 무기를 뒤로 당김 |
| 2 | `af:2, afy:-2` | `[20, 16]` | 던지기 — **이 프레임에서 투사체 엔티티를 스폰한다** |
| 3 | `af:2, afy:-1` | `[25, 17]` | 릴리스 — 손을 떠남 |
| 4 | `af:1` | `[31, 17]` | 복귀 — 화면 밖 |

**창과 단검은 2행짜리 얇은 형태다.** 처음에 3행 십자 형태로 그렸더니 창이 아니라 망치로 보였다.
32px 화면에서 투사체는 얇을수록 궤도가 잘 읽힌다.

투사체가 실제로 스폰되는 시점은 프레임 2, 즉 공격 입력 후 약 100ms다.
[02](02-core-mechanics.md#24-공격)의 발사 딜레이 3프레임(50ms)과 후딜 8프레임을 여기에 맞춘다.

## 12.7 렌더 코드

```ts
export function paint(
  ctx: CanvasRenderingContext2D,
  matrix: readonly string[],
  palette: Record<string, string>,
  ox: number, oy: number, px = 1
): void {
  for (let y = 0; y < matrix.length; y++) {
    const row = matrix[y]
    for (let x = 0; x < 32; x++) {
      const ch = row[x]
      if (!ch || ch === '.') continue
      const color = palette[ch]
      if (!color) continue
      ctx.fillStyle = color
      ctx.fillRect(ox + x * px, oy + y * px, px, px)
    }
  }
}
```

행 길이는 로드 시 32로 검증한다. 한 글자만 어긋나도 그 아래 전체가 밀린다.

### 파편 샘플링

갑옷 파괴 시 파편 24개는 **이 매트릭스의 실제 픽셀에서 뽑는다.** 임의 파티클이 아니라
방금까지 입고 있던 갑옷이 부서지는 것으로 보여야 한다.

```ts
const armorPixels = matrix.flatMap((row, y) =>
  [...row].map((ch, x) => '1234'.includes(ch) ? { x, y, color: palette[ch] } : null)
).filter(Boolean)
```

### 공정성 장치

| 규칙 | 이유 |
|---|---|
| 화면 밖 스폰 금지 | 반드시 화면 안에서 대기 상태로 먼저 보인다. 안 보이는 곳에서 날아오면 부당한 죽음이 된다 |
| 반경 120px 진입 시 이륙 | 플레이어가 거리를 통제할 수 있다 |
| 착지 후 3초 정지 | 잡을 수 있는 틈을 명시적으로 준다 |

**노란 눈(`5`)이 유일한 고채도 색이다.** 어두운 스테이지 1에서 그림의 위치를 즉시 읽게 하는
시각 신호이며, 이것 없이는 안개 속에서 실루엣이 묻힌다.

> **구현 (`src/sprite/enemies.ts`)** — 14×16 통 프레임 3장(비행 2 · 대기 1).
> 파츠로 나누지 않았다: 이 크기에서는 접합부가 스프라이트보다 커진다.
> 팔레트는 위 표 그대로이고, 노란 눈은 **대기 상태에도 그대로 보인다** —
> 화면 안에서 먼저 보여야 한다는 공정성 규칙이 대기 상태에 걸려 있기 때문이다.
> 명도 검증은 `src/sprite/enemies.test.ts` 가 강제한다 (눈이 몸보다 3배 이상 밝을 것).
>
> **옆모습이다.** 처음에는 정면으로 그려 놓았는데, 12.6 이 "측면 스크롤 게임의
> 플레이 스프라이트는 처음부터 측면으로 설계해야 한다" 고 못박은 것을 어긴
> 상태였다. 날개는 뒤(왼쪽)로 쓸리고 노란 눈은 앞(오른쪽)에 하나만 보인다 —
> 눈이 둘 보이면 어디를 노리는지 읽을 수 없다. 오른쪽을 보게 그리고,
> 렌더러가 `scale.x = enemy.facing` 으로 뒤집는다.

## 12.10 캐른 (Cairn) — 스테이지 1 보스

**HP 300 · 56×52 · 3페이즈.** 시체와 묘비가 뭉쳐진 덩어리.
뷰어: [`cairn.html`](cairn.html)

### 파츠 분할이 곧 페이즈 3 메카닉이다

캐른은 다른 스프라이트와 분할 원칙이 다르다. 랜슬의 파츠가 **애니메이션을 위한 분할**이라면,
캐른의 파츠는 **페이즈 3 패턴 그 자체**다.

```
페이즈 1~2   BASE + ARM_BACK + TORSO + CORE + HEAD + ARM   (한 덩어리)
페이즈 3     몸통 분해 → HEAD · ARM · ARM_BACK · BASE 가 개별 추적
             남은 것은 CORE 하나 — 약점이 그대로 드러난다
```

여기서 설계가 하나 맞물린다. **분해는 곧 약점 노출이다.**
파편 4개가 쫓아오는 동안 코어는 무방비로 떠 있고, 플레이어는 선택해야 한다 —
파편을 피하는 데 집중할 것인가, 위험을 감수하고 코어를 때릴 것인가.

원작 계승 관점에서도 맞다. 튜토리얼 보스가 가르쳐야 할 것은 "패턴을 외워라"가 아니라
**"뛰기 전에 읽어라"**이고, 이 구간이 그 판단을 처음으로 강제한다.

> 따라서 파츠는 렌더 편의가 아니라 **판정 단위**다. 파편 4개는 각각 히트박스를 갖고,
> 재결합 시 원래 오프셋으로 돌아온다. 분할을 바꾸면 패턴도 바뀐다.

코어 파괴 → **400ms 히트스톱** → 화이트아웃 → 몸통이 시체 단위로 흩어지며 무너진다.

파편은 랜슬의 갑옷 파괴와 **같은 방식으로 실제 픽셀에서 샘플링한다.**
`1`~`4`(돌)와 `5`,`6`(뼈)를 나눠 뽑아 돌 파편은 무겁게, 뼈 파편은 가볍게 날린다.

### 게임 연결 (`src/sprite/cairn.ts` · `src/render/cairnRenderer.ts`)

`tools/sprite/parts.json` 의 파츠를 그대로 옮기고, 위 클립 표를 `cairnPose()` 로 구현했다.
예비 프레임 수는 `entities/bosses/cairn.ts` 의 `CAIRN` 상수와 **테스트로 묶여 있다** —
어긋나면 예비가 끝난 뒤에도 팔이 들려 있어 "언제 맞는지"를 읽을 수 없다.

코어 오프셋 `(23, 26, 10, 10)` 이 판정 코어와 같은지도 테스트가 검사한다.
보이는 약점과 맞는 약점이 다르면 페이즈 3 이 성립하지 않는다.

> 페이즈 3 분해 상태는 **테스트로만 검증했다.** 화면에서 눈으로 확인하지 못했다 —
> 분해 패턴이 무작위로 뽑히는 데다 그 구간에서 살아남기가 어려워 포착에 실패했다.
> 파편 렌더 경로는 본체와 같고, 파편 4개와 파츠의 대응은 `makeFragments` 의
> 오프셋과 대조해 고정해 두었다.

### 알려진 한계 — 아트 패스 필요

이 매트릭스는 **그레이박스 등급**이다. 인카운터를 만들고 히트박스·타이밍을 맞추기에는
충분하지만, 그대로 출시할 품질은 아니다. M1 아트 패스에서 손으로 다시 찍는다.

| 항목 | 상태 |
|---|---|
| 크기감 (플레이어 대비 2배) | 확정 |
| 코어 가독성 | 확정 — 고채도 보라가 즉시 읽힌다 |
| 파츠 분할 · 오프셋 | 확정 — 페이즈 3 메카닉과 맞물려 있어 바꾸지 않는다 |
| 팔 접합부 | **미흡** — 어깨가 몸통에 묻히지 않아 별개 블록으로 읽힌다 |
| 표면 질감 | **미흡** — "시체와 묘비가 뭉친" 느낌보다 석상에 가깝다 |

> 팔 접합은 폭 프로파일 생성으로는 해결되지 않았다. 어깨는 몸통 실루엣과
> 겹쳐 그려야 하고, 그건 손으로 찍어야 하는 작업이다.
