# 10. 기술 스펙

> M0 착수(2026-08) 이후 이 문서는 **구현이 따라야 할 규격**이다.
> 정확한 의존성 버전은 `package.json` 이 단일 진실 원천이고, 여기 적힌 것은 메이저 버전이다.

---

## 10.1 스택 선정

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | TypeScript 7.x | 타입 안정성. 게임 상태 머신이 많은 프로젝트일수록 이득 |
| 렌더러 | **PixiJS v8 (WebGL 고정)** | 필터 파이프라인 성숙, 픽셀아트 지원 우수 |
| 빌드 | Vite | 빠른 HMR. 게임 개발은 반복 확인 속도가 생산성을 지배 |
| 배포 | Vercel (정적) | 기존 파이프라인 재사용 |
| 오디오 | Howler.js | 스프라이트 시트, 페이드, 다중 스템 재생 지원 |
| 물리 | **직접 구현** | 플랫포머 물리는 라이브러리보다 커스텀이 정답 |
| 레벨 | Tiled (`.tmj`) | 성숙한 에디터, JSON 출력 |
| 스프라이트 | Aseprite → TexturePacker | |
| 테스트 | Vitest | 물리·상태 머신 단위 테스트 |

### PixiJS 선택 근거

| 후보 | 판단 |
|---|---|
| **PixiJS v8** | ✅ 채택. 필터 체인이 우리 셰이더 스택과 직결 |
| Phaser 3 | 물리·씬 관리가 내장이지만 커스텀 물리를 쓸 거면 오히려 무겁다 |
| 순수 WebGL2 | 통제력 최상이나 스프라이트 배칭·아틀라스를 전부 직접 짜야 함 |
| Godot 4 웹 익스포트 | 초기 로드 20MB+ (WASM 런타임). 웹 우선 프로젝트에 부적합 |

> **WebGL 로 고정한 이유 (M1-4).** 커스텀 셰이더를 GLSL 한 벌로 유지하기 위해서다.
> WebGPU 를 함께 지원하려면 같은 효과를 WGSL 로 한 벌 더 관리해야 하는데,
> 480×270 논리 해상도에서 WebGPU 의 이점은 측정되지 않는다. M4 성능 작업에서 재검토한다.

> **Godot을 배제한 것이 이 기획의 중요한 결정이다.**
> Godot 웹 빌드는 첫 로드가 무겁고 모바일 브라우저 호환이 불안정하다.
> "클릭 한 번에 시작"이라는 우리의 핵심 이점을 해친다.

### 설계 원칙

**불변 상태 갱신.** 게임 상태는 매 틱마다 새 객체로 만든다.

```ts
// 지양
function updateBody(body: Body, dt: number): void {
  body.x += body.vx * dt  // 원본 변경
}

// 지향
function updateBody(body: Body, dt: number): Body {
  return { ...body, x: body.x + body.vx * dt }
}
```

리플레이 저장, 롤백, 디버깅이 전부 쉬워진다.
성능이 문제되는 핫패스(파티클 400개 등)만 예외적으로 풀링 + 가변 처리한다.

**파일 크기**: 200~400줄 기준, 800줄 초과 금지. 초과 시 분할.

## 10.3 게임 루프

```
픽스드 타임스텝 60Hz + 렌더 보간
```

| 항목 | 값 |
|---|---|
| 로직 틱 | 정확히 1/60초 (16.667ms) |
| 최대 캐치업 | 프레임당 5틱 (스파이럴 방지) |
| 렌더 | requestAnimationFrame, 틱 간 알파로 위치 보간 |
| 히트스톱 | 로직 틱만 정지, 렌더·입력 폴링은 계속 |

**결정론적 로직이 필수다.** 리듬 동기(S3), 리플레이, 리그레션 테스트가 전부 여기 의존한다.
부동소수점 누적 오차를 피하기 위해 물리는 고정 dt만 사용한다.

## 10.4 물리

### AABB 스윕 콜리전

| 항목 | 처리 |
|---|---|
| 브로드페이즈 | 타일맵 그리드 질의 (엔티티 AABB가 걸치는 타일만) |
| 내로페이즈 | 축 분리 해결 — X축 먼저, 그 다음 Y축 |
| 최대 이동 | 틱당 이동량이 타일 크기(16px) 초과 시 서브스텝 분할 |
| 원웨이 플랫폼 | 하강 중 + 이전 프레임에 위에 있었을 때만 충돌 |
| 붕괴 타일 | 접촉 후 60틱(1초) 뒤 충돌 비활성 + 접촉 즉시 시각 예고 |

### 엔티티-엔티티 충돌

| 쌍 | 처리 |
|---|---|
| 플레이어 ↔ 적 | AABB 겹침 → 피격 (무적 아닐 때) |
| 투사체 ↔ 적 | AABB 겹침 → 데미지 + 소멸 |
| 투사체 ↔ 타일 | 무기별 (관통/반사/소멸) |
| 적 ↔ 적 | **충돌 없음** — 겹쳐도 무방 |

**공간 분할은 초기에 넣지 않는다.** 동시 엔티티가 최대 30 수준이므로 브루트포스로 충분하다.
프로파일링 후 필요할 때만 도입.

## 10.5 렌더링 파이프라인

```
1. 씬 렌더 (레이어 1~7)      → colorRT
2. 발광 오브젝트만 렌더        → emissiveRT
3. 광원 누적                  → lightRT
4. colorRT × lightRT          → litRT
5. emissiveRT → 블룸 3패스    → bloomRT
6. litRT + bloomRT (additive) → composedRT
7. 왜곡 · 색수차 · 비네트 · 그레인 → screen
```

| 렌더 타겟 | 해상도 | 용도 |
|---|---|---|
| colorRT | 480×270 | 씬 |
| emissiveRT | 480×270 | 발광 마스크 |
| lightRT | 240×135 (1/2) | 광원 누적 (저해상도로 충분) |
| bloomRT | 240×135 → 120×68 → 60×34 | 블룸 다운샘플 |

**논리 해상도에서 전부 처리하고 마지막에만 업스케일한다.**
1080p에서 포스트 처리를 하면 픽셀당 비용이 16배가 된다.

### 업스케일

논리 480×270 → 정수 배율 nearest-neighbor 업스케일.
비정수 배율이 필요한 창 크기에서는 **레터박스**를 넣고 정수 배율을 유지한다.
픽셀 크기가 불균등해지는 것이 검은 여백보다 나쁘다.

## 10.6 에셋 파이프라인

## 10.7 로딩 & 용량 예산

| 시점 | 대상 | 누적 용량 |
|---|---|---|
| 초기 (첫 조작까지) | 엔진 + common 아틀라스 + S1 에셋 + UI SFX + S1 BGM | **~7.5MB** |
| S1 플레이 중 | S2 에셋 백그라운드 프리페치 | |
| 각 스테이지 진입 | 해당 아틀라스 + 오디오 | 스테이지당 ~4MB |
| 보스룸 30초 전 | 보스 BGM 프리로드 | |
| 전체 | | **~55MB** |

| 항목 | 예산 |
|---|---|
| JS 번들 (gzip) | 400KB 이내 |
| 초기 로드 총량 | **8MB 이내** |
| 첫 조작까지 시간 | 3G에서 15초, 광랜에서 2초 |

**초기 8MB는 타협 불가 지표다.** 이걸 넘으면 웹 플랫폼을 고른 이유가 사라진다.

> **빌드가 이걸 강제한다.** `npm run build` 마지막에 `scripts/check-size.mjs` 가
> `dist` 를 재고, 넘으면 종료 코드 1 로 죽으면서 큰 파일부터 알려 준다.
> Vercel 도 같은 명령을 돌리므로 **예산을 넘긴 빌드는 배포되지 않는다.**
> 소스맵은 세지 않는다 — 개발자 도구를 열기 전에는 받지 않는다.
>
> 런타임 계측(`telemetry/loadSize.ts`)은 테스터가 실제로 받은 바이트를 재지만
> 그건 이미 배포된 뒤다. 둘이 하는 일이 다르다.
>
> 현재: **0.60MB / 8MB (7.5%)** — 소스맵 제외, 압축 전.

## 10.9 테스트 전략

| 레벨 | 대상 | 도구 |
|---|---|---|
| 단위 | 물리(AABB, 스윕), 데미지 계산, 상태 머신 전이, 점수 | Vitest |
| 통합 | 스테이지 로드 → 클리어 판정, 세이브 왕복 | Vitest |
| 결정론 | **동일 입력 시퀀스 → 동일 최종 상태** | Vitest (골든 테스트) |
| 성능 | 프레임 예산 회귀 감지 | 자동 벤치 스크립트 |
| E2E | 타이틀 → S1 클리어 자동 플레이 | Playwright + 입력 리플레이 |

### 결정론 골든 테스트가 핵심이다

입력 시퀀스를 녹화해두고, 물리·밸런스 수정 후 재생했을 때
**최종 상태가 달라지면 알림**이 뜨도록 한다.
플랫포머에서 "점프 높이가 1px 바뀐 것"을 사람이 눈으로 잡는 것은 불가능하다.

### 커버리지 목표

| 영역 | 목표 |
|---|---|
| `physics/` | 95% |
| `game/`, `entities/` 상태 머신 | 85% |
| 전체 | 80% |
| `sprite/` | 95% — 순수 데이터라 전부 검증 가능하다 |
| `fx/` | 85% — 타이밍과 물리는 검증 대상, 그리기는 제외 |
| `render/` | 제외 (시각 검증으로 대체) |
| `telemetry/` | 95% — 게이트 판정의 근거라 틀리면 프로젝트가 잘못된 방향으로 간다 |
| `scenery/` | 95% (분기 70%) — 남은 분기는 `noUncheckedIndexedAccess` 가 강제하는 도달 불가 가드다 |
| `ui/` | 제외 (시각 검증으로 대체) |
| `core/bgm.ts`, `core/sfx.ts` | 제외 — WebAudio 는 node 에서 돌지 않는다. 오프라인 렌더로 실측한다 (docs/07 7.2) |

| 무적 / 무한 잔기 | 레벨 검수용 |
| 슬로우모션 | 0.1x~1.0x — 연출 프레임 검수 · **F7** |
| 프레임 스텝 | 한 틱씩 진행 — 히트박스 검증 · **Shift+F8** 로 켜고 **F8** 로 한 칸 |
| 밸런스 핫리로드 | `data/*.json` 수정 시 재시작 없이 반영 |
| 리플레이 녹화·재생 | 버그 재현 + 결정론 테스트 |
| 게이트 판정 패널 (F6) | 재시도율·프레임 유지율·시도 횟수 실시간 계측 → `prompts/m1-gate.md` |

> **시간 제어는 로직에 손대지 않는다** (`src/core/timeControl.ts`).
> 루프에 넣는 `frameMs` 만 바꾸므로 결정론이 유지되고, 프레임 스텝으로 본 것이
> 실제로 일어나는 것과 같다. 연출(`BreakDirector`)도 같은 시간을 받는다 —
> 슬로우모션이 연출에 안 걸리면 검수가 안 된다.
>
> **개발 빌드에서만 동작한다.** 테스터가 실수로 눌러 시간이 느려지면
> 프레임 유지율 계측이 통째로 거짓이 된다.
>
> 실측: 30프레임에 실시간 31틱 → 0.5x 15틱 → 0.25x 7틱.
> 스텝 모드에서는 요청한 만큼만 정확히 나아간다 (3회 요청 → 3틱).

**이 도구들을 만드는 시간은 낭비가 아니다.**
게임 개발에서 반복 확인 속도가 최종 품질을 결정한다.
