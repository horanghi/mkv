# M1 게이트 — 이 프로젝트의 진짜 관문

**스테이지를 늘리기 전에 반드시 통과한다.** 여기서 실패한 채로 M2에 들어가면
같은 결함을 6개 스테이지에 복제하게 된다.

## 측정 항목

추측하지 말고 계측한다. **빌드가 직접 센다** — 아래 표의 여섯 항목은 전부
`src/telemetry/` 가 재고 있고, 개발자는 F6 으로 판정을 본다.

| 지표 | 합격선 | 의미 |
|---|---|---|
| **사망 후 즉시 재시도율** | **≥ 90%** | 가장 중요. 미달이면 어려운 게 아니라 불공정한 것 |
| 60fps 유지 | 중급 노트북에서 95% 프레임 | |
| 첫 클리어 시도 횟수 | 8~15회 | 5회 미만이면 쉽고, 25회 초과면 이탈 |
| "죽는 연출이 좋았다" | 70% 이상 | 이 게임의 판매 포인트 |
| 초기 로드 | 8MB 이하 | 웹을 고른 이유 |
| 사망 → 조작 가능 | 3초 이하 | |

**여섯 중 둘은 이미 판정됐다** — 사람이 필요 없는 항목이라 빌드가 직접 잰다.

| 지표 | 실측 | 판정 |
|---|---|---|
| 초기 로드 | 0.61MB / 8MB (7.7%) | 통과 (`npm run build` 가 매번 잰다) |
| 사망 → 조작 가능 | 1.75초 / 3초 | 통과 (틱 단위 실측) |

나머지 넷은 **테스터 다섯**이 있어야 숫자가 생긴다. 여기서 멈춘다.

## 재시도율이 낮을 때

난이도를 낮추기 전에 원인을 분리한다.

| 증상 | 원인 | 조치 |
|---|---|---|
| 같은 지점에서 반복 사망 후 이탈 | 그 구간이 판독 불가 | 레벨 수정 (카메라 선행, 예고 신호) |
| 죽고 나서 화면을 오래 봄 | 재시작 마찰 | 연출 단축, 페이드 축소 |
| 무엇에 죽었는지 모름 | 시각 신호 부족 | 적 대비 강화, 투사체 크기 |
| 그림에게만 죽음 | 스폰 규칙 위반 | 화면 밖 스폰 여부 재점검 |

각 조치의 손잡이가 어디 있는지 미리 적어 둔다 — 미달이 나온 뒤에 찾으면 늦다.

| 조치 | 손잡이 |
|---|---|
| 카메라 선행 | `game/camera.ts` — 데드존과 **따로** 보간한다 (더하면 두 배가 된다) |
| 예고 신호 | `entities/bosses/cairn.ts` 의 `windupFrames` · 그림의 `dormant` |
| 연출 단축 · 페이드 축소 | `fx/sequence.ts` 의 `DEATH_TIMING` |
| 적 대비 강화 | `sprite/enemies.ts` 의 팔레트 (그림의 노란 눈이 그 예다) |
| 투사체 크기 | `entities/bosses/hazard.ts` 의 `SIZES` — **적** 투사체를 말한다 |
| 스폰 규칙 | `entities/enemies/grimm.ts` · `world.ts` 가 `viewOf(camera)` 를 넘긴다 |

## 통과 후

M2로 넘어가되, 이 지표들을 각 스테이지마다 다시 측정한다.
M1에서 세운 기준선이 이후 모든 밸런싱의 기준이 된다.

---

## 어떻게 재는가

지표마다 정의가 하나여야 한다. 정의가 흔들리면 테스터끼리 숫자를 못 합친다.

| 지표 | 조작적 정의 | 상수 |
|---|---|---|
| 즉시 재시도율 | **조작이 돌아온 뒤 3초 안에 입력이 들어왔는가.** 판정이 끝난 사망만 분모에 넣는다. **다시 죽은 것도 재시도다** — 죽으려면 계속해야 한다 | `RETRY_WINDOW_MS` |
| 60fps 유지율 | 프레임 간격이 **20ms 이하**인 프레임의 비율 | `FRAME_HELD_MS` |
| 첫 클리어 시도 횟수 | **사망 횟수 + 1**. 클리어 시점에 확정한다 | — |
| 초기 로드 | 같은 출처에서 받은 바이트 합 (캐시면 압축 본문 크기) | `GATE.loadBytes` |
| 사망 → 조작 가능 | 사망 틱부터 조작이 돌아온 틱까지의 **최댓값**. 틱 정밀 (프레임 단위로 재면 한 프레임씩 늦게 잡힌다) | `GATE.controlBackMs` |

### 판정하지 않는 경우

표본이 모자라면 `pass` 도 `fail` 도 아닌 **`unknown`** 이다. 통과로 읽으면 안 된다.

- 사망 5회 미만 → 재시도율 판정 없음 (`MIN_DEATHS`)
- 프레임 1800개 미만(약 30초) → fps 판정 없음 (`MIN_FRAMES`)
- 미클리어 → 시도 횟수 판정 없음

### 부활하자마자 다시 죽는 경우

가장 몰입한 행동인데, 처음 구현에서는 **이탈로 세어졌다.** 한 프레임에 여러
로직 틱이 도는데 부활 틱과 사망 틱이 같은 프레임에 들어오면 조작 복귀가
관측되지 않기 때문이었다. 실기에서 5번 중 1번이 거짓 이탈로 잡혔다.

두 곳을 고쳤다.

1. 부활을 **틱 단위로** 보고한다. 프레임 앞뒤 비교만으로는 놓친다.
2. 새 사망이 기록되면 판정이 남은 직전 사망을 **재시도로 확정한다.**
   창을 넘긴 경우는 매 프레임 도는 `observe` 가 이미 이탈로 닫았으므로,
   여기까지 남아 있다는 건 아직 창 안이라는 뜻이다.

기록 순서도 규칙이다 — **복귀 → 입력 → 사망.** 복귀와 입력은 *직전* 사망에
붙으므로 새 사망을 밀어 넣기 전에 처리해야 한다.

### 버리는 프레임

- 시작 직후 90프레임 — 셰이더 컴파일·텍스처 업로드 구간이다
- 250ms 이상의 간격 — 탭을 접으면 브라우저가 rAF 를 멈춘다. 성능이 아니라 브라우저 동작이다

계측 시계는 벽시계가 아니라 **그려진 프레임의 누적**이다. 탭을 접어 둔 시간이
플레이 시간으로 잡히거나, 플레이어가 아무것도 안 했는데 재시도 창이 만료되면 안 된다.

## 테스터에게 주는 것

**지표를 보여주지 않는다.** 재시도율을 재는 걸 알면 억지로 다시 하고,
프레임을 재는 걸 알면 프레임을 본다. 테스터가 보는 것은 두 가지뿐이다.

1. 클리어하면 뜨는 카드 — "죽는 연출이 마음에 들었나요", "점프가 답답했나요"
2. 5번 넘게 죽으면 오른쪽 아래에 생기는 **결과 보내기** 버튼 (끝까지 못 간 사람도 보낼 수 있어야 한다)

카드의 **결과 복사**를 누르면 400자 남짓의 JSON 이 클립보드에 들어간다.
그걸 그대로 받아 합치면 된다. 개인을 가리키는 값은 담기지 않는다 —
`id` 는 브라우저에서 만든 난수이고, 같은 사람이 두 번 붙여넣은 것을 걸러내는 용도다.

기록은 `localStorage` 에 남아 **탭을 닫았다 다시 열어도 이어진다.**
"첫 클리어까지 몇 회"는 한 번에 끝내지 않는 사람에게도 성립해야 하기 때문이다.

**판정 규칙이 바뀌면 `SESSION_VERSION` 을 올린다.** 항목이 그대로여도 재는
방식이 바뀌면 섞을 수 없다 — 같은 자리에 다른 뜻의 숫자가 들어 있다.
올리면 낡은 기록은 버려지고 테스터는 처음부터 다시 센다.
(v1 → v2: 위 "부활하자마자 다시 죽는 경우" 를 고치면서 올렸다.
v2 → v3: 난이도를 기록하기 시작했다.)

### 어느 난이도에서 재는가

**기사(기본)에서 잰다.** 합격선은 한 난이도에 대한 숫자다 — 종자에서 10회와
성기사에서 10회는 다른 뜻이므로, 섞어서 평균 내면 어느 쪽도 아닌 값이 나온다.
docs/08 이 "기록은 조합별로 분리한다"고 정한 것과 같은 이유다.

일시정지 메뉴에서 난이도를 바꾸면 **계측 세션이 새로 시작된다.** 이어 붙이면
한 꾸러미 안에 서로 다른 규칙에서 잰 사망이 섞이기 때문이다. 테스터에게는
"난이도를 건드리지 말 것"을 먼저 말한다 — 바꾸는 순간 그때까지의 기록이
사라진다.

### 합칠 때

`retryRate` 는 사망 수로 가중해 합친다 (단순 평균이 아니다 — 두 번 죽은 사람과
서른 번 죽은 사람의 무게가 같으면 안 된다). `deathFxLiked` 는 사람 수로 센다.
`hotspots` 를 여러 명 것에서 겹쳐 보면 "판독 불가 구간"이 바로 드러난다.

**손으로 합치지 않는다.** 위 규칙은 `src/telemetry/aggregate.ts` 에 있고,
찍는 것은 CLI 다.

```
npm run gate -- results.txt        # 파일 (여러 개 가능)
cat results.txt | npm run gate     # 파이프
```

테스터에게 보낼 글은 [`m1-gate-testers.md`](m1-gate-testers.md) 에 있다.
**무엇을 재는지는 알리지 않는다** — 관찰된다는 걸 알면 행동이 바뀐다.

입력은 메신저에서 긁어온 그대로 넣어도 된다 — 사람이 쓴 글 사이에서 JSON 만
골라낸다. 메신저가 따옴표를 굽은 것으로 바꿔 놨어도 읽는다. 그래도 못 읽은
것은 **몇 건인지 찍는다** — 조용히 버리면 다섯이 보냈는데 넷으로 판정된다.
같은 `id` 가 두 번 오면 오래 플레이한 쪽만 남긴다.
**`SESSION_VERSION` 이 다른 꾸러미는 뺀다** — 저장소가 낡은 기록을 버리는 것과
같은 이유다. 버전을 올린 뒤에는 그 전 결과를 다시 받아야 한다.

**빌드가 갈리면 알려 주되 빼지는 않는다.** 꾸러미의 `build` 는 번들 파일의
내용 해시라, 코드가 한 글자만 달라져도 값이 바뀐다. 다만 오타 하나 고친
빌드와 밸런스를 바꾼 빌드를 기계가 구분할 수 없으므로 판단은 사람이 한다 —
그 사이에 수치를 만졌다면 다시 받고, 아니라면 합쳐도 된다.
배포 경로가 둘 이상일 때(민찬 게임랜드의 `mkv/` 와 자체 배포) 특히 본다.
로드 용량과 부활 시간은 **평균이 아니라 최악값**으로 본다 (한 명이라도 3초를
넘겼으면 넘긴 것이다). 테스터가 5명 미만이면 판정은 `표본부족` 이고,
그건 통과가 아니다.
